Konfiguration

Parameter & Secrets

🔐 Secret — kein Default

var pwd = builder.AddParameter(
  "rabbitmq-password",
  secret: true);

→ Gespeichert in dotnet user-secrets
→ Kein Wert = Fehler beim Start

⚙️ Parameter — mit Default

var cap = builder.AddParameter(
  "cookie-jar-capacity",
  config["Parameters:cookie-jar-capacity"]
    ?? "100"); // Default im Code

→ Kein Secret, kein user-secrets nötig
→ Injiziert als CookieJar__Capacity 

# Lokal setzen
dotnet user-secrets set \
  "Parameters:rabbitmq-password" \
  "supersecret"

⚠️ AddParameter(name, "100") ist eine Konstante — user-secrets werden ignoriert.
Gefunden von einem Test → gleich mehr dazu.

- Unterschied secret vs. plain Parameter klar machen - secret: true → Aspire verlangt Wert aus user-secrets oder env var — kein Default möglich (Sicherheit!) - plain parameter: Default in Code, überschreibbar — gut für Feature-Konfiguration - Falle: AddParameter(name, value) setzt einen festen Wert, KEINEN Default. In der DWX-Version war genau das drin — Override per user-secrets hat nie gewirkt - Aufgefallen ist es erst durch den E2E-Test (Capacity 42 erwartet, 100 bekommen) → Überleitung zum Testing-Teil - IOptionsMonitor: live reload wenn Config sich ändert, ohne Neustart

Testen mit Aspire

Aspire.Hosting.Testing

Das AppHost ist die Test-Fixture — dieselbe Topologie wie lokal 🧪

🧩 Modell-Tests

ohne Docker · < 1 s 
await using var builder = await DistributedApplicationTestingBuilder
  .CreateAsync<Projects.CookieJar_AppHost>(
    ["Parameters:cookie-jar-capacity=80"]);

var capacity = builder.Resources
  .OfType<ParameterResource>()
  .Single(r => r.Name == "cookie-jar-capacity");

Assert.Equal("80", await capacity.GetValueAsync(ct));
  • Nur das Modell bauen — Replicas, WaitFor, Health Checks, Parameter prüfen
  • Schnell genug für jeden PR-Build

🚀 E2E-Tests

echte Container 
App = await builder.BuildAsync(ct);
await App.StartAsync(ct);
await App.ResourceNotifications
  .WaitForResourceHealthyAsync("server", ct);

// Zugriff wie ein echter Client
var http = App.CreateHttpClient("server");
var db   = await App.GetConnectionStringAsync("cookiejardb");
var mq   = await App.GetConnectionStringAsync("messaging");
  • Startet PostgreSQL, RabbitMQ, 2 Server-Replicas — einmal pro Test-Collection
  • Keine Ports, keine Connection Strings im Testcode
- NuGet: Aspire.Hosting.Testing — Test-Projekt referenziert das AppHost-Projekt wie eine Library - DistributedApplicationTestingBuilder: gleicher Builder wie im AppHost, aber im Testprozess - Zwei Ebenen: Modell-Tests (nur Builder, kein Start) und E2E-Tests (BuildAsync + StartAsync) - Modell-Tests: laufen ohne Docker in Millisekunden — ideal für PR-Builds - E2E: echte Container, echte Prozesse, dieselbe Verdrahtung wie bei "aspire run" - CreateHttpClient geht über den Aspire-Proxy, GetConnectionStringAsync liefert die aufgelösten Werte - Abgrenzung zu Testcontainers / WebApplicationFactory: dort baut man die Topologie im Test nach — hier ist sie schon da
Testen mit Aspire

Das AppHost für Tests umbauen

// Parameter als Konfiguration — keine user-secrets auf dem Build-Agent
var builder = await DistributedApplicationTestingBuilder
  .CreateAsync<Projects.CookieJar_AppHost>(
    ["Parameters:rabbitmq-password=e2e-test",
     "Parameters:cookie-jar-capacity=42"]);

// Kein UI, kein zufälliger Sensor (inkl. npm/pip-Installer)
foreach (var r in builder.Resources.Where(r =>
    r is PgAdminContainerResource
    || r.Name.StartsWith("frontend")
    || r.Name.StartsWith("cookie-sensor")).ToList())
  builder.Resources.Remove(r);

// Leere DB — nie das Volume der lokalen Entwicklung anfassen
var postgres = builder.Resources.Single(r => r.Name == "postgres");
foreach (var m in postgres.Annotations
    .OfType<ContainerMountAnnotation>().ToList())
  postgres.Annotations.Remove(m);

Modell ist nur Daten

Ressourcen und Annotations vor BuildAsync() entfernen, ersetzen, ergänzen.

Ressourcen umkonfigurieren

CreateResourceBuilder<ProjectResource>("api")
→ .WithEnvironment(…) für Fakes,
→ .WithHttpHealthCheck(…) für Readiness

Replicas einzeln ansprechen

Der http-Endpoint ist der Aspire-Proxy. Der Port pro Replica steht in ASPNETCORE_URLS — via ResourceNotifications.WatchAsync().

- Das Schöne: das App-Modell ist vor BuildAsync nur eine Liste von Ressourcen mit Annotations — frei veränderbar - Parameter per Argument statt user-secrets — CI braucht keine Geheimnisse - UI-Container (PgAdmin) und der zufällige Python-Sensor fliegen raus — Tests senden Events selbst, deterministisch - Stolperstein Aspire 13.6: AddViteApp / AddPythonApp erzeugen eigene Installer-Ressourcen (frontend-installer, cookie-sensor-installer) — die muss man mit entfernen - Data Volume entfernen: jeder Lauf startet mit leerer DB, lokale Entwicklerdaten bleiben unberührt - Replicas: ASPNETCORE_URLS aus dem Resource-Snapshot — so kann man gezielt Replica 1 und 2 testen
Testen mit Aspire

🍪 Die Keksdose unter Test

🧪 CookieJar.Tests

Demo 1 
[Fact]
public async Task CookieTakenEvent_LowersLevel_OnBothReplicas()
{
  await PublishCookieTakenAsync(amount: 7);  // direkt in RabbitMQ

  // RabbitMQ gibt das Event an EINE Replica —
  // beide müssen den neuen Stand aus der DB sehen
  foreach (var replica in fixture.Replicas)
    Assert.Equal(93, await WaitForLevelAsync(replica, 93));
}
# 5 Tests, ~10 s inkl. Container-Start
dotnet test src/CookieJar.Tests

# Bekannten Bug live zeigen
dotnet run --project src/CookieJar.Tests -- -explicit only

🐞 Was die Tests gefunden haben

Parameter ignoriert Konfiguration

Refill mit Capacity 42 erwartet — 100 bekommen. AddParameter(name, "100") war eine Konstante. Behoben.

SSE-Updates nur von einer Replica

Erwartet [100, 99, 98, 97, 96] — Replica 1 sieht [100, 99, 98]. Die Channel<int>-Abos leben im Speicher der Replica. Bewusst offen.

Beide Bugs sind mit einer Instanz und ohne echte Konfiguration unsichtbar — mit WithReplicas(2) im Test fallen sie sofort auf.

- DEMO: dotnet test src/CookieJar.Tests — 3 Modell-Tests + 2 E2E-Tests, grün in ~10 s - Dashboard läuft im Test nicht mit, aber Logs der Ressourcen landen im Test-Logger - Bug 1 (Parameter): DWX-Version hatte AddParameter(name, "100") — der Wert ist fest, Konfiguration wird ignoriert. Test erwartet 42 aus dem Argument und bekommt 100. Fix: Konfiguration lesen, 100 nur als Fallback - Bug 2 (SSE): Explicit-Test zeigen: dotnet run -- -explicit only. RabbitMQ verteilt die Events auf beide Replicas (Competing Consumers), aber jede Replica benachrichtigt nur ihre eigenen SSE-Clients - Bug 2 ist absichtlich nicht behoben — Fix wäre z. B. Fanout-Exchange oder Postgres LISTEN/NOTIFY. Guter Diskussionspunkt - Explicit-Tests laufen nicht im normalen Lauf — CI bleibt grün, der Bug bleibt dokumentiert und ausführbar
Testen mit Aspire · Aus der Praxis

Zwei Kundenprojekte

📦 Projekt A — Auslieferungs-Service

2 Replicas · PostgreSQL · Redis · S3 (LocalStack)

// Container nur für diesen Lauf — keine geteilten Daten
foreach (var r in appHost.Resources.OfType<ContainerResource>())
{
  foreach (var a in r.Annotations.OfType<ContainerLifetimeAnnotation>().ToList())
    r.Annotations.Remove(a);
  r.Annotations.Add(new ContainerLifetimeAnnotation
    { Lifetime = ContainerLifetime.Session });
}
// Upstream-System als In-Process-Fake im Testprozess
appHost.CreateResourceBuilder<ProjectResource>("api")
  .WithEnvironment("UPSTREAM_URL", fakeUpstream.Url);

// Chaos: Storage einfrieren, Verhalten prüfen
await DockerAsync("pause", storageContainerId);
  • Migration-Lock & Cron-Job: läuft genau 1× pro Tick, nicht pro Replica
  • Storage-Ausfall → Cache liefert, sonst 503 + Retry-After
  • Nightly (~8 min), Opt-in per Env-Variable, CI bricht bei 0 Tests ab

🖥️ Projekt B — Fachanwendung mit Web-UI

API · Web-UI · PostgreSQL · Playwright

appHost.CreateResourceBuilder<ProjectResource>("api")
  // Echtes Fremdsystem unerreichbar machen
  .WithEnvironment("EXTERNAL__MASTERDATA__BASEADDRESS",
                   "http://127.0.0.1:9")
  // "Healthy" = API lebt und verlangt Auth
  .WithHttpHealthCheck("/v1/me", statusCode: 401);

// Testdaten direkt in die DB
await TestData.SeedAsync(NpgsqlDataSource.Create(
  await app.GetConnectionStringAsync("app-db")));

// Browser: Testnutzer per API-Key in die UI-Config
await context.RouteAsync("**/app-settings.json", …);
  • Ein Test pro Akzeptanzkriterium — UI, API & DB in einem Durchlauf
  • Playwright-Trace nur bei Fehlschlag gespeichert
- Beide Beispiele anonymisiert aus aktuellen Kundenprojekten - Projekt A: Service mit 2 Replicas, die sich Postgres, Redis und S3 teilen - Fake für das Upstream-System läuft als Minimal-API im Testprozess, zählt Requests — Tests prüfen "wurde wirklich nachgeladen?" - Container-Lifetime auf Session: lokale Entwickler nutzen persistente Container — Tests dürfen die nicht teilen - Chaos-Test: docker pause auf LocalStack (stop würde den Bucket löschen) → Output-Cache liefert weiter, ungecachte Dateien 503 mit Retry-After, Readiness bleibt grün - Replica-Logs werden über einen eigenen ILoggerProvider mitgeschnitten und im Test ausgewertet ("Acquired the migration lock" genau 2×) - Läuft nachts, ~8 Minuten; Projekt ist nur mit Env-Variable ein Testprojekt, damit "dotnet test" im PR-Build es überspringt - Projekt B: Fachanwendung, Tests sind direkt aus Akzeptanzkriterien abgeleitet - AppHost wird einmal pro Testlauf gestartet (xUnit v3 AssemblyFixture), Testdaten per SQL geseedet - Externes Stammdatensystem auf einen toten Port umgebogen — kein Test ruft je das echte System - Health Check umdefiniert: 401 auf einem geschützten Endpoint heißt "bereit" - Playwright: verschiedene Testnutzer, indem die UI-Konfiguration per Route-Interception umgeschrieben wird - Erfahrung: Aufwand liegt im Umbau des AppHost für Tests und in stabilen Wartebedingungen, nicht im Testcode selbst

🚢 Kamal — als NuGet-Paket

Demo 4 · Open Source 
# dotnet add package Vensas.Aspire.Hosting.Kamal

builder.AddKamalEnvironment("kamal")
  .WithServers(vmIp)
  .WithRegistry(registry, "unused")
  .WithProxyHostSuffix($"{vmIp}.nip.io");

server.PublishAsKamalService((_, config) =>
  config.Proxy!.Healthcheck = new() { Path = "/health" });

# deploy.yml pro App, .kamal/secrets, Dockerfiles
aspire publish --output-path ./deploy/output/kamal
  • Echtes Compute-Environment statt Einmal-PipelineStep
  • github.com/vensas/aspire-hosting-kamal
- Kubernetes: AddKubernetesEnvironment → Helm-Chart via aspire publish — Preview - Known Issues: Ingress-Resource fehlt, etc. — für Produktion nacharbeiten - Accessories als Deployments im Helm-Chart — für Produktion besser: externe Managed Services (RDS, ElastiCache) - Kamal: von 37signals (Basecamp, Hey) — "deploy anywhere, no Kubernetes needed" - Zur DWX war das ein Custom PipelineStep im Demo-Repo — jetzt ist daraus ein Open-Source-Paket geworden: Vensas.Aspire.Hosting.Kamal auf NuGet - AddKamalEnvironment ist ein IComputeEnvironmentResource — gleiche Liga wie AddDockerComposeEnvironment / AddKubernetesEnvironment - PublishAsKamalService: typisiertes deploy.yml-Modell pro Ressource anpassbar (Proxy-Host, Health Check, Rollen) - nip.io: Hostnamen für eine lokale VM ohne eigene Domain; SSL aus, weil kein Let's Encrypt möglich

Aspire MCP

KI-Tooling mit Anwendungskontext

MCP macht Aspire zum Kontext-Provider für Agenten 🤖

Was der MCP-Server bereitstellt

  • Laufende Ressourcen & deren Status
  • Structured Logs live abrufbar
  • Traces & Metrics
  • Aspire Dokumentation durchsuchbar

Echter Mehrwert heute

  • Schnelles Onboarding: KI versteht die Architektur sofort
  • Live-Diagnose: "Warum schlägt Service X fehl?"
  • Testing: KI kann Ressourcen direkt abfragen
# MCP-Server einrichten
aspire agent init  # konfiguriert claude_desktop_config.json oder andere MCP-fähige Tools
- MCP = Model Context Protocol — standardisiertes Interface für KI-Tools zu externen Systemen - aspire agent init richtet den MCP-Server ein — dann kann Claude/Copilot direkt auf die Aspire-App zugreifen - Demo: KI fragt "welche Services laufen?" und bekommt echte Antwort aus dem Dashboard - Diagnose-Szenario: KI liest Logs eines fehlerhaften Services und gibt sofort Kontext - Work in Progress, aber schon heute nützlich
Lessons Learned

TL;DR

✅ Echter Mehrwert

  • Lokale Entwicklung — massiver Zeitgewinn, gesamter Stack mit einem Befehl
  • Beschreibungssprache näher am Entwickler
  • Tech-Stack-Unabhängigkeit: Python, Node, Dockerfile — kein .NET-Zwang
  • Debugging verteilter Systeme: WaitFor, Replicas, Observability out-of-the-box
  • Aspire.Hosting.Testing: E2E-Tests gegen dasselbe AppHost — fand 2 Bugs in der Demo
  • Aspire MCP: Produktionsbugs lokal reproduzieren, Logs vergleichen — Kontext für Agenten

⚠️ Deployment-Realität

  • Docker Compose: verbessert sich, aber für echte Produktion noch Handarbeit
  • Kubernetes: Preview — Helm-Output ist Ausgangspunkt, nicht Endprodukt
  • Eigener Provider (Kamal): als Paket wiederverwendbar — das Provider-Modell trägt
  • Außerhalb Azure gilt: Deployment nicht unterschätzen — Aspire allein reicht nicht
- Lokale Entwicklung: massiver Zeitgewinn — gesamter Stack, Hot Reload, Observability, kein Docker-Compose-Handarbeit - Tech-Stack-Unabhängigkeit: Python Sensor, Node Frontend, .NET Backend — alles in einem AppHost. Kein .NET-Zwang. - Debugging: .WithReplicas(2) — CookieJarService SSE-Bug reproduzierbar. Replicas enthüllen Race Conditions die mit einer Instanz unsichtbar sind. - Testing: Aspire.Hosting.Testing macht das AppHost zur Test-Fixture. Modell-Tests im PR, E2E nightly. In der Demo zwei echte Bugs gefunden (Parameter-Konstante, SSE pro Replica). - Aspire MCP: KI hat direkten Zugriff auf laufende Resources, Logs, Traces — nicht nur Code-Kontext. Das ist 2026 der interessanteste Trend. - Azure: azd up liest AppHost-Model, generiert Bicep, provisioniert Container Apps, PostgreSQL, Service Bus. Kein manuelles Infra-Wissen nötig. - Docker Compose: verbessert sich schnell, aber Secrets im .env sind leer, TLS manuell, kein aspire build — noch Lücken - Kubernetes: Preview — Ingress fehlt, Secrets als Plaintext, Accessories als Deployments (nicht produktionstauglich) - Kamal: aus dem DWX-Machbarkeitsnachweis ist Vensas.Aspire.Hosting.Kamal geworden. Das Compute-Environment-Modell von Aspire trägt auch Nicht-Microsoft-Ziele — Lücken bleiben (z. B. buildx vs. Podman). - Fazit: Aspire ist kein "deploy anywhere"-Tool. Für lokale Dev und Azure: sofort empfehlenswert. Rest: abwarten oder mitgestalten.
