Konfiguration

Parameter & Secrets

🔐 Secret — kein Default

var pwd = builder.AddParameter(
  "rabbitmq-password",
  secret: true);

→ Gespeichert in dotnet user-secrets
→ Kein Wert = Fehler beim Start

⚙️ Parameter — mit Default

var cap = builder.AddParameter(
  "cookie-jar-capacity",
  "100"); // Default im Code

→ Kein Secret, kein user-secrets nötig
→ Injiziert als CookieJar__Capacity 

# Lokal setzen
dotnet user-secrets set \
  "Parameters:rabbitmq-password" \
  "supersecret"

Beide Typen fließen als Umgebungsvariablen in die Services

- Unterschied secret vs. plain Parameter klar machen - secret: true → Aspire verlangt Wert aus user-secrets oder env var — kein Default möglich (Sicherheit!) - plain parameter: Default in Code, überschreibbar — gut für Feature-Konfiguration - IOptionsMonitor: live reload wenn Config sich ändert, ohne Neustart

Deployment · Teil 1

Azure & Docker Compose

☁️ Azure — First-Class Citizen

nicht Teil der Demo 
# Azure Developer CLI — ein Befehl reicht:
azd init  # azure.yaml + Bicep generieren
azd up    # Infra + App provisionieren & deployen
  • Aspire → Bicep: Container Apps, PostgreSQL Flexible Server, Service Bus
  • azd up liest AppHost-Model
  • Azure Key Vault für Secrets, Azure Monitor für Telemetrie
  • Nicht alle Aspire-Ressourcen haben 1:1-Azure-Pendant

🐳 Docker Compose

Demo 1 
// AppHost.cs
builder.AddDockerComposeEnvironment("docker-compose")
  .ConfigureComposeFile(compose => {
    compose.Services["messaging"].Healthcheck = …;
  });

# Artifacts generieren:
aspire publish --output-path ./deploy/output

# Starten:
docker compose -f ./deploy/output/docker-compose.yaml up
  • Generiert: docker-compose.yaml
  • AddDockerfile für non-.NET Container (nginx, Python, …)
  • ConfigureComposeFile: Healthchecks & Restart-Policies nachträglich ergänzen
- Azure: azd (Azure Developer CLI) liest das AppHost-Model und generiert Bicep - Container Apps für Services, Managed PostgreSQL, Service Bus für RabbitMQ-Ersatz - Azure ist first-class citizen - nicht Teil der Demo - Docker Compose: AddDockerComposeEnvironment als Resource registrieren, dann aspire publish - ConfigureComposeFile: läuft nach der Generierung — hier Healthchecks, DependsOn-Conditions etc.
Deployment · Teil 2

Kubernetes & Custom Providers

☸️ Kubernetes / Helm

Demo 2 · Preview 
// AppHost.cs
builder.AddKubernetesEnvironment("kubernetes");

# Helm-Chart generieren:
aspire publish --output-path ./deploy/output

# Deployen:
helm upgrade --install cookiejar \
  ./deploy/output/kubernetes/
  • Generiert Helm-Chart und values.yaml
  • ⚠️ Preview-Feature
  • Ausgabe ist Ausgangspunkt, kein produktionsfertiges Chart

⚙️ Custom Provider — Kamal

Demo 3 · Experimental 
// AppHost.cs — eigenen PipelineStep registrieren
builder.AddResource(new KamalDeploymentResource("kamal")
  { ServiceName = "cookiejar", Architecture = "arm64",
    ExtraSecretEnvVars = ["CookieJar__Capacity"] })
  .WithPipelineStepFactory(KamalPipelineStep.Create);

# Kamal-Artifacts generieren:
aspire publish --output-path ./deploy/output

# VM einrichten + deployen:
kamal deploy ...
  • Custom PipelineStep liest das AppHost-Modell aus
  • Generiert config/deploy.yml + .kamal/secrets.example
- Kubernetes: AddKubernetesEnvironment → Helm-Chart via aspire publish — Preview - Known Issues: Ingress-Resource fehlt, etc. — für Produktion nacharbeiten - Accessories als Deployments im Helm-Chart — für Produktion besser: externe Managed Services (RDS, ElastiCache) - Kamal: von 37signals (Basecamp, Hey) — "deploy anywhere, no Kubernetes needed" - KamalDeploymentResource: Custom pipeline, konfigurierbar - Dockerfile-Container mit EndpointAnnotation (frontend, nginx) → HTTP-Accessory auf Port 3000; ohne Endpoint (cookie-sensor) → Worker-Accessory, kein Port, Connection Strings aus Secrets - RequiredBySteps = ["publish"] bedeutet: läuft MIT aspire publish
Aspire MCP

KI-Tooling mit Anwendungskontext

MCP macht Aspire zum Kontext-Provider für Agenten 🤖

Was der MCP-Server bereitstellt

  • Laufende Ressourcen & deren Status
  • Structured Logs live abrufbar
  • Traces & Metrics
  • Aspire Dokumentation durchsuchbar

Echter Mehrwert heute

  • Schnelles Onboarding: KI versteht die Architektur sofort
  • Live-Diagnose: "Warum schlägt Service X fehl?"
  • Testing: KI kann Ressourcen direkt abfragen
# MCP-Server einrichten
aspire agent init  # konfiguriert claude_desktop_config.json oder andere MCP-fähige Tools
- MCP = Model Context Protocol — standardisiertes Interface für KI-Tools zu externen Systemen - aspire agent init richtet den MCP-Server ein — dann kann Claude/Copilot direkt auf die Aspire-App zugreifen - Demo: KI fragt "welche Services laufen?" und bekommt echte Antwort aus dem Dashboard - Diagnose-Szenario: KI liest Logs eines fehlerhaften Services und gibt sofort Kontext - Work in Progress, aber schon heute nützlich
Lessons Learned

TL;DR

✅ Echter Mehrwert

  • Lokale Entwicklung — massiver Zeitgewinn, gesamter Stack mit einem Befehl
  • Beschreibungssprache näher am Entwickler
  • Tech-Stack-Unabhängigkeit: Python, Node, Dockerfile — kein .NET-Zwang
  • Debugging verteilter Systeme: WaitFor, Replicas, Observability out-of-the-box
  • Aspire MCP: Produktionsbugs lokal reproduzieren, Logs vergleichen — Kontext für Agenten

⚠️ Deployment-Realität

  • Docker Compose: verbessert sich, aber für echte Produktion noch Handarbeit
  • Kubernetes: Preview — Helm-Output ist Ausgangspunkt, nicht Endprodukt
  • Custom Provider (Kamal): machbar — aber Aufwand sollte den Nutzen rechtfertigen
  • Außerhalb Azure gilt: Deployment nicht unterschätzen — Aspire allein reicht nicht
- Lokale Entwicklung: massiver Zeitgewinn — gesamter Stack, Hot Reload, Observability, kein Docker-Compose-Handarbeit - Tech-Stack-Unabhängigkeit: Python Sensor, Node Frontend, .NET Backend — alles in einem AppHost. Kein .NET-Zwang. - Debugging: .WithReplicas(2) — CookieJarService SSE-Bug reproduzierbar. Replicas enthüllen Race Conditions die mit einer Instanz unsichtbar sind. - Aspire MCP: KI hat direkten Zugriff auf laufende Resources, Logs, Traces — nicht nur Code-Kontext. Das ist 2026 der interessanteste Trend. - Azure: azd up liest AppHost-Model, generiert Bicep, provisioniert Container Apps, PostgreSQL, Service Bus. Kein manuelles Infra-Wissen nötig. - Docker Compose: verbessert sich schnell, aber Secrets im .env sind leer, TLS manuell, kein aspire build — noch Lücken - Kubernetes: Preview — Ingress fehlt, Secrets als Plaintext, Accessories als Deployments (nicht produktionstauglich) - Custom Provider: Machbarkeitsnachweis — wer Kamal kennt und einsetzt, profitiert. Aber: echt viel Aufwand für die Integration. - Fazit: Aspire ist kein "deploy anywhere"-Tool. Für lokale Dev und Azure: sofort empfehlenswert. Rest: abwarten oder mitgestalten.
