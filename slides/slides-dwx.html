Konfiguration

Parameter & Secrets

🔐 Secret — kein Default

var pwd = builder.AddParameter(
  "rabbitmq-password",
  secret: true);

→ Gespeichert in dotnet user-secrets
→ Kein Wert = Fehler beim Start
→ Production: Azure Key Vault, Kubernetes Secrets 

# Lokal setzen
dotnet user-secrets set \
  "Parameters:rabbitmq-password" \
  "supersecret"

⚙️ Parameter — mit Default

var cap = builder.AddParameter(
  "cookie-jar-capacity",
  "100"); // Default im Code

→ Kein Secret, kein user-secrets nötig
→ Injiziert als CookieJar__Capacity
→ IOptionsMonitor<T> im Service

Beide Typen fließen als Umgebungsvariablen in die Services —
Aspire übernimmt Naming Convention und Injection.

- Unterschied secret vs. plain Parameter klar machen - secret: true → Aspire verlangt Wert aus user-secrets, env var oder Key Vault — kein Default möglich (Sicherheit!) - plain parameter: Default in Code, überschreibbar — gut für Feature-Konfiguration - IOptionsMonitor: live reload wenn Config sich ändert, ohne Neustart - Prod: gleiche AppHost-Definition, andere Secret-Quelle (Key Vault, K8s Secrets)
Unter der Haube

Wie Aspire intern funktioniert

🖥️

Dashboard — kein externer Service

Teil des AppHost-Prozesses. Services senden OTLP via Env-Var-konfiguriertem Endpoint direkt an den AppHost-internen Collector. Daneben läuft ein gRPC-Backchannel für Ressourcenstatus, Live-Logs und Commands wie aspire publish.

🧩 Annotations-Modell

Alles ist ein IResource. Der Builder akkumuliert nur Annotations (ContainerImageAnnotation, WaitForAnnotation …).
Build() materialisiert das Modell — danach nur noch Ausführung.

🔗 WithReference — Env Var Injection

.WithReference(db) hängt eine EnvironmentCallbackAnnotation an.
Beim Start löst Aspire den Ausdruck auf und setzt
ConnectionStrings__<name> — kein fixer Port im Code.

🔍 Service Discovery

Aspire setzt services__server__http__0=http://localhost:PORT.
AddServiceDefaults() registriert einen Resolver,
der IConfiguration auswertet → http://server funktioniert.

❤️ WaitFor — mehr als Port-Polling

Interne State Machine: Starting → Running → Healthy.
.WaitFor(x) blockiert bis Zielzustand erreicht,
nicht nur bis der Port offen ist.

- Annotations: Builder ist ein reiner Konfigurations-Akkumulator — Build() ist der Moment wo alles zusammenkommt - WithReference: der entscheidende Mechanismus — erklärt warum keine Ports hardcodiert sind - Service Discovery: ServiceEndpointResolver aus Aspire.ServiceDefaults — zeigen wie die Env Var aussieht - WaitFor: State Machine zeigt im Dashboard — Starting, Running, Healthy sichtbar - Dashboard: Backchannel ist auch die Basis für aspire publish und MCP — der rote Faden

Deployment

Docker Compose & Kubernetes

ℹ️ Azure ist first-class citizen in Aspire (Container Apps, AZD, Azure-Hosting-Integrationen) — in diesem Vortrag fokussieren wir uns auf Docker und Kubernetes.

🐳 Docker Compose

aspire publish \
  --output-format docker-compose \
  --output-path ./deploy/docker

docker compose \
  -f ./deploy/docker/docker-compose.yml \
  up --build
  • docker-compose.yml mit allen Services
  • Volumes & Networking generiert
  • Gut für: Single-Server, Staging
  • Image-Push zu Registry unterstützt

☸️ Kubernetes / Helm

aspire publish \
  --output-format helm \
  --output-path ./deploy/helm

helm upgrade --install cookiejar \
  ./deploy/helm -n cookiejar
  • Helm Chart mit Deployments, Services
  • ConfigMaps & Secrets generiert
  • aspire deploy --list-steps (experimentell)
  • Ingress: manuell nötig
- Azure nicht vergessen zu erwähnen: azd up, Container Apps, Azure-Hosting — aber nicht Thema heute - Docker Compose: vollständig generiert — Services, Volumes, Networking, .env-Datei - Helm: guter Ausgangspunkt, Ingress und TLS muss man selbst konfigurieren - aspire deploy: Pipeline-basiert, experimentell in 13 — zeige --list-steps wenn Zeit - Beide Targets kommen aus der gleichen AppHost-Definition — das ist der Kernwert
Custom Deployment Adapter

Kamal — eigener Publisher

Was ist Kamal?

  • Docker auf Bare-Metal oder Cloud-VMs
  • Kein Kubernetes — SSH + Docker reicht
  • Zero-downtime Deploy, Rolling Restart
  • kamal setup && kamal deploy
# Generieren
aspire publish \
  --output-path ./deploy/kamal

# Ausgabe:
#   deploy.yml
#   .kamal/secrets.example

PipelineStep implementieren

var step = new PipelineStep {
  Name = "generate-kamal-config",
  Action = async ctx => {
    var output = ctx.Services
      .GetRequiredService<
        IPipelineOutputService>();
    // Generiert deploy.yml + .kamal/secrets
  }
};
step.RequiredBy(
  WellKnownPipelineSteps.Publish);
// In AppHost.cs registrieren:
builder.AddResource(
    new KamalDeploymentResource("kamal"))
  .WithPipelineStepFactory(
    KamalPipelineStep.Create);
- Kamal: von 37signals (Basecamp/Rails) — "deploy anywhere, no Kubernetes" - PipelineStep statt IDistributedApplicationPublisher — neues API in Aspire 13 (noch experimental) - Step walks the resource model: PostgresServerResource → Kamal accessory, ProjectResource → main service - IPipelineOutputService liefert den Output-Pfad — kein IOptions mehr nötig - RequiredBy(WellKnownPipelineSteps.Publish): Step läuft automatisch bei aspire publish - Output zeigen: deploy.yml + .kamal/secrets.example
Aspire MCP · kurz

KI-Tooling mit Anwendungskontext

# MCP-Server einrichten
aspire agent init

# → konfiguriert claude_desktop_config.json
# → oder andere MCP-fähige KI-Tools

Was der MCP-Server bereitstellt

  • Laufende Ressourcen & deren Status
  • Structured Logs live abrufbar
  • Traces & Metrics
  • Aspire Dokumentation durchsuchbar

Echter Mehrwert heute

  • Schnelles Onboarding: KI versteht die Architektur sofort
  • Live-Diagnose: "Warum schlägt Service X fehl?"
  • Testing: KI kann Ressourcen direkt abfragen

Fazit: MCP macht Aspire zum strukturierten Kontext-Provider für KI-Tools — das ist der interessanteste Aspire-Trend 2026.

- MCP = Model Context Protocol — standardisiertes Interface für KI-Tools zu externen Systemen - aspire agent init richtet den MCP-Server ein — dann kann Claude/Copilot direkt auf die Aspire-App zugreifen - Demo: KI fragt "welche Services laufen?" und bekommt echte Antwort aus dem Dashboard - Diagnose-Szenario: KI liest Logs eines fehlerhaften Services und gibt sofort Kontext - Work in Progress, aber schon heute nützlich
Lessons Learned

Was Aspire kann — und was noch nicht

⚠️ Herausforderungen

  • Helm-Output ist Ausgangspunkt, nicht Endprodukt — Ingress & TLS manuell
  • Polyglot-Debugging: Python- & Node-Services haben keinen Aspire-nativen Debugger
  • Deployment-Features (Pipeline, Dockerfile Builder) noch experimentell
  • Azure-Parität: nicht alle Aspire-Ressourcen haben ein 1:1-Azure-Pendant

✅ Bewährte Patterns

  • WaitFor konsequent nutzen — nie auf Timeouts verlassen
  • Alle Credentials als Parameter — auch lokal, auch wenn es "nur dev" ist
  • Aspire für Orchestrierung, nicht als Application Framework
  • AddServiceDefaults() in jedem Service — Observability kostet nichts
  • .WithReplicas(2) — Produktionsprobleme durch Replica-Interferenz lokal nachstellen
- Das ist die ehrliche Seite — was ich Kunden und Teams sage bevor sie Aspire einführen - Herausforderungen sind keine Deal-Breaker, aber man muss sie kennen - Patterns: WaitFor ist fast immer die richtige Antwort auf Startup-Probleme - "Aspire für Orchestrierung, nicht als Framework": Aspire soll verdrahten, nicht die App-Logik bestimmen - WithReplicas: konkretes Beispiel aus dem Demo — CookieJarService hat In-Memory-Subscriber-Liste für SSE. Mit einer Instanz funktioniert alles. Mit zwei Replicas: Keks wird auf Replica A genommen, DB-Update passiert, aber Broadcast geht nur an SSE-Clients die auf Replica A verbunden sind — Clients auf Replica B sehen keine Live-Updates. Genau so ein Bug tritt in Produktion auf, und mit .WithReplicas(2) kann man ihn lokal sofort reproduzieren und fixen (z.B. Redis Pub/Sub). - Fazit insgesamt: Aspire spart massiv Zeit bei lokaler Entwicklung, beim Deployment ist man noch nicht am Ziel
