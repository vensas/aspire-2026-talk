| 7 | Parameters and secrets | `secret: true` has no default: user secrets or an environment variable. `AddParameter(name, "100")` is a constant and ignores the configuration. Read the configuration first. `CapacityParameter_ReadsConfiguration` and the refill test guard this. |
| 8 | How Aspire works | DCP is a Go binary (dcp + dcpctrl) with a Kubernetes-like API. The AppHost talks to it with the KubernetesClient package — not gRPC. DCP also starts the dashboard as a separate process; the services send OTLP to it directly. No ports in the code: WithReference and service discovery give them as environment variables. WaitFor: show the Starting → Running → Healthy states in the dashboard. |
| 9 | Test the real app | The test project references the AppHost like a library. Model tests run in the PR build; E2E tests start real containers. Compare: with Testcontainers or WebApplicationFactory you build the topology again in the test. |
| 10 | Prepare the AppHost for the test | Walk through the three numbered changes. Step 2 also removes the npm and pip installer resources that Aspire 13.6 adds. The test changes only its own copy of the model. |
| 11 | Two replicas show a bug | **Demo:** `dotnet run --project src/CookieJar.Tests -- -explicit only`. RabbitMQ is a competing consumer: each event goes to one replica, and SSE subscriptions are in memory per replica. Thus each replica streams only its own events. Kept on purpose as a discussion point; a fix is a fanout exchange or Postgres LISTEN/NOTIFY. The other tests pass (`dotnet test`, 6 tests): the refill returns the capacity parameter, and `BothReplicas_MigrateUnderTheLock` checks the advisory lock around MigrateAsync through the replica logs. |
| 12 | Project A | Anonymized. The upstream fake is a minimal API in the test process and counts the requests. `docker pause`, not `stop` — stop deletes the bucket. Replica logs go to a custom ILoggerProvider ("Acquired the migration lock" two times). |
| 13 | Project B | Anonymized. The AppHost starts one time per run (xUnit v3 AssemblyFixture). Playwright users come from route interception of the UI configuration. |
| 14 | Docker Compose | **Demo:** `deploy/docker-compose/1-publish.sh` … `3-deploy.sh`. Azure: `azd up` generates Bicep — not in the demo. |
| 15 | Kubernetes and Kamal | **Demo:** `deploy/kubernetes/*` and `deploy/kamal/*`. Kubernetes output is a preview: no ingress, secrets need work. Kamal: from 37signals, deploy without Kubernetes. `Vensas.Aspire.Hosting.Kamal` is an open-source compute environment, like Compose and Kubernetes. |
| 16 | Inside the Kamal package: your own deployment target | How to build a deployment target with the Aspire API, shown on `Vensas.Aspire.Hosting.Kamal` (`KamalEnvironmentResource.cs`). 1: `AddKamalEnvironment` adds the resource only in publish mode. 2: three pipeline steps — prepare (after `ValidateComputeEnvironments`, adds a `DeploymentTargetAnnotation` to each compute resource), publish (required by `Publish`, writes to `IPipelineOutputService`), kamal deploy (required by `Deploy`). 3: a project or a Dockerfile resource is a Kamal app with its own config; other containers are accessories — Kamal boots them once and does not redeploy them. They all go into the config of the first app, thus the sensor is declared after the server. 4: `EnvironmentCallbackAnnotation` callbacks give the env vars that `WithReference` set; a secret `ParameterResource` becomes a `.kamal/secrets` reference; `GetHostAddressExpression` makes an endpoint the container name on the kamal network. The YAML is the result that the demo deploys. |
| 17 | Aspire MCP: the agent sees the running app | **Demo:** ask the agent why replica 2 does not stream the new level. `aspire agent init` sets up the MCP server. The image on the slide is a real answer from the Aspire MCP tools (`list_structured_logs` against the running AppHost) — the fallback if the live demo is slow. |
| 18 | TL;DR | End on the AI point. Step 3 gives the maturity of each deployment target: Azure (azd) and Compose are stable, Kubernetes is a preview, Kamal is a community package (0.1.x). For architects: Aspire adds little for one service without dependencies, or when a platform team owns the deployment — then use it for local development and tests only. Try it: `aspire new`, then `aspire run`. The QR code on the next slide has the demo. |
